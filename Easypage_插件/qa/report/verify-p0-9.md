### 3.2 `startIn` 收不收目录句柄 —— `qa/probes/save-picker-startin-capability.mjs` **8/8 PASS**

（起本地 http 服务，用 `navigator.storage.getDirectory()` 拿**真 OPFS 句柄** —— `file://` 上 OPFS 被拒。）

| 传入 | 结果 | 判读 |
|---|---|---|
| 无 `startIn` | `rejected:AbortError` | 基准：选项通过、框开不成 |
| `'documents'`（已知合法） | `rejected:AbortError` | 同上 |
| **真目录句柄** | `rejected:AbortError` | **与已知合法值同类型 ⇒ 被接受** |
| 伪句柄 `{kind:'directory'}` | `rejected:TypeError` | 被拒 |
| 数字 `123` | `rejected:TypeError` | 被拒 |

⇒ **差分对照成立**：「自动定位到原文件所在处」有 API 依据。

> ⚠️ **这个探针我第一版写错了断言**：把「选项被拒」写成「**同步**抛 `TypeError`」，跑出 **2 项假 FAIL**。
> 实测五格的 `syncThrew` **全为 `null`** —— 选项校验是**异步**的，`TypeError` 出现在 promise rejection 里。
> **这是「假证据」的又一幅面孔：测量没错，判据挂错了通道（同步 vs 异步）。**
> 判别式改为「看错误类型」后 8/8。同时删掉了一段用空参数真去调 picker 的死代码。
> 另：一次点击只能开一个系统框 —— `showDirectoryPicker` 会耗尽 transient activation，
> 所以这个探针**不能**在同一页里连着调两个 picker（结论也已写进 `dir-save.ts` 的文件头）。

## 四、实现（两个模块 + 五处改动）

### `src/extension/inline-deps.ts`（新增，核心）

纯函数式：**输入清理后的副本 + 一个读字节的回调，输出内联后的副本 + 失败清单**。
覆盖四类内联：① 页内 `<style>` 的 `url()`；② `<link rel=stylesheet>` → `<style>`（含 `media` 包 `@media`）；
③ `<script src>` → 内联 `<script>`；④ 图片/媒体/字体 → `data:` URI（含 `srcset`、`poster`、`object[data]`）。
css 内 `@import` **递归展开**（深度上限 8，防互相 import 打转），相对 `url()` **相对那个 css 文件**解析。

三条纪律（写进文件头）：

1. 🔴 **绝不往用户文件里加标记属性。** 一开始想加 `data-ep-inlined-from` 记溯源，立刻否掉：
   `stripArtifacts` / `collectResidue` 认的正是 `data-ep-*`，加了等于自己给自己埋残留 ⇒
   **保存会被自己的护栏拦下**。
2. **读不到的依赖进失败清单，不静默降级。** 静默产出一份「看起来自包含、其实是坏的」文件，
   用户拉出去分享才会发现坏 —— 那是最坏的失败方式。
3. **只搬字节，不改逻辑。** 唯一的例外是 `defer` 的**位置**。

必须处理的两个边界（规格里原本没写，实现时才发现）：

- 🔴 **`<script>` / `<style>` 是原始文本元素**：内容里出现 `</script` 会把标签提前截断 ⇒ 转义成 `<\/script`。
- 🔴 **`defer` 内联后失效**（内联脚本忽略它、就地立即执行）⇒ 带 `defer` 的脚本必须**挪到 `</body>` 前**。

明确的覆盖边界（如实标注，不假装）：`<iframe src>` **不内联**（等于搬进整份子文档）⇒ 进失败清单；
css 用正则而非完整解析器（注释里的 `url(...)` 会被误当成真引用，无害）；**运行时 `fetch`/`XHR` 做不到**。

> 🔴 **② 的记忆粒度在 G1 两格验完后被放宽过一次**（2026-09-23，用户裁决「你就改进吧」）：
> 原键是**文档级**的（`dir:<完整文件路径>`）⇒ 同一个目录里每打开一个新 html 都要重选一次目录。
> 现在主用**目录级**键（`dirScopeKeyOf`：`dir:file:///C:/proj/`），文档级键只用于**读取**升级前的
> 旧值（用户不必因为键换了粒度再选一次）。两级键**恒不会相撞**：目录级键恒以 `/` 结尾。
> ⚠️ 这不破坏 P0-7 的防护 —— 那条防的是「A 页面拿到 B 页面的**文件**句柄」（键在文件粒度上）；
> 目录句柄被同目录的文件共享，本来就是正确语义。
>
> `startIn` 传的是 `RECENT_DIR_KEY`（最近一次成功用过的目录），**只在它的
> `queryPermission({ mode: 'readwrite' }) === 'granted'` 时才传** —— `startIn` 收到无权限句柄时
> Chromium 可能直接抛错，而**一次点击只够开一个框**，我们没有重试的资本。它只影响框开在哪，
> **绝不参与决定落点**（否则换项目目录时会静默把副本存到别处）。
> 写成功之后记两个键：目录级（供同目录复用）+ 最近（供目录框定位）。

`@deprecated`，两条路径共用同一套克隆/清理，不会漂移）；`toast.ts` / `bar.ts` 文案与状态重写；
`content.ts` 装配 `dirPicker` + `savePicker`；`vite.config.ts` 加 `disableIframePageLoading`。

## 六、🔴 本轮抓到的 bug（两个，都是真的）

### 6.1 `dirReader` 违反了自己文件头写下的契约

函数头写着「**读不到一律返回 null，永不抛**」，而实现只把「路径切分与 `..` 判断」放在外面，
`getFileHandle` / `getFile` 抛的 `NotFoundError` / `NotAllowedError` **直接漏给调用方**。

后果不是「报错难听」，而是**语义被换掉**：调用方拿到的是「**内联流程崩了**」，
而它该拿到的是「读不到」——两者的处置完全不同（前者进失败清单走 base 兜底，后者会让整次保存失败）。

- **发现方式**：新写的单测 `不存在的文件返回 null（不抛）` 挂了。这不是测试写错，**是产品错了**。
- **修法**：整段 `try/catch` 兜住，返回 `null`。
- **教训**：**实现必须对得上自己写下的契约**；契约写在注释里不等于实现遵守了它。

### 6.2 `saveInfo` 的字段被耦合在一起

`bar.ts` 旧实现是「只要传了 `deps` 就整体替换 `saveInfo`」，于是 `dir` / `target` **只在同时传 `deps` 时才生效**。
症状是「只想改个文件名」的调用**静默失效**，提示里写着上一次的名字 —— 不报错、也不明显。
⇒ 改为**逐字段更新**（`deps` 与 `more` 成对，其余各自独立），并补一条单测钉住。

### 6.3 顺带修的两处「文档与代码不符」

- `save.ts` 的 `@deprecated` 注释仍指 `saveToWorkDir`（已不存在）⇒ 改指 `saveCopy`。
- `SaveResult.direct` 的注释停留在 P0-8 语义 ⇒ 改写真值条件（**一个系统框都没弹**），
  并写明「别把它读成『用了记忆里的目录』：那是『少弹一个框』，不是『没弹框』」。

## 八、G1 怎么跑（给人看的三句话）

`npm run qa:g1`（或双击根目录 `verify-writeback.cmd`），它会：

1. 先构建扩展，再跑 `--self-test` —— **不开浏览器**就验证那 22 条判据有没有判别力；
2. 起浏览器 + 装扩展，**自动造一份沙盘**（`test-results/g1/`：css / js / 根图 / **子目录图** 各一份）；
3. 让你做三件事：点「编辑模式」→ 改几个字 → 点「**另存为副本**」并在**目录框**里选中沙盘目录；
4. 你选完之后，它**读盘校验 + 把副本单独拷到只有它的文件夹里重开一遍**，

   那这一轮什么都没证明）。

> 🔴 **第二轮改了口径（静默保存）**：手动门禁从「按回车」变成「选目录」，
> 三条眼睛判据换成 —— ① 目录框是否停在原目录；② **选完之后是否真的不再弹第二个框**
> （这是「静默」的唯一证据，因为没有别的可观测物）；③ 自动打开的标签页里是否看得到 `manual-page_改.html`。
> ⚠️ 必然还会看到**浏览器自己**的「允许修改文件」——那是写权限确认，不是我们的框，去不掉。

P0-9 的**行为**（同目录 `原名_改.html`、依赖内联、不覆写原文件、缺手势可退化）在

**不能自动化的那两格：一格已关，一格只剩弱证据。**
· **G1 真机** —— ✅ **已关**（§3.3）：保存框**停在原目录** + 文件名**已预填**，两项都由用户实机人眼确认。
· **真实目录句柄能否读到依赖字节** —— ⚠️ **仍没有证据**。用户那次保存成功、提示里没有 ⚠️，

  （那正是本项目最怕的假证据：判据没有判别力，却给出绿灯）。

> 「自包含」这一格已从「无证据」升到「有直接证据」：`qa:selfcontain` 跑的是产品自己的 `saveCopy()`，

## 十、🔴 这一轮探针自己犯了三个「假证据」（全部已修，登记在此防复发）

第二轮升级探针时，第一稿跑出 **10 条 FAIL，条条指向产品**；查完之后**没有一条是产品的问题**。
三次是三种不同的「假证据面孔」，已升格写进 `ui-probe-false-evidence-guard` skill 的 ⑩⑪⑫：

| # | 现象 | 真因 | 对应形态 |
|---|---|---|---|
| 1 | css / js 被内联成**空内容**（`<style></style>`、`<script defer=""></script>`） | 夹具把**字符串**交给页面时写成 `Array.from(new Uint8Array(v))` —— `new Uint8Array('字符串')` **不做编码**，按 `.length` 造出**全 0 数组**。css/js 因此变成一串 NUL，产品照章办事把它们内联成「非空但全是 NUL」的内容。**二进制夹具碰巧没事**（`new Uint8Array(Buffer)` 是对的）⇒ 假象更逼真：图能加载、文本不能 | **⑩ 夹具喂进去的数据不是它声称的那份** ⇒ 加「**开浏览器之前**的夹具自检」 |
| 2 | 「`@import` 残留」 | 判据 `/@import/` 扫产物，命中的是夹具自己那段**可见文字**「@import 展开测试」。产品其实展开得好好的 | **⑫ 正则扫产物被自己夹具里的同一串字点亮** ⇒ 夹具文案避开该字串，判据改成语法形状 `/@import\s+(?:url\()?["']/i` |
| 3 | `#set`（`srcset` 图）「加载失败」 | 判据 `naturalWidth > 0`，而 **`naturalWidth` 是按选中候选的密度折算过的**：1×1 的 `2x` 候选 = `1/2` 取整 = **0**。定点实验实测：`<11×13> 2x` 报 `5×6`、`<1×1> 2x` 报 `0×0`、单候选 `1x` 报 `1×1` | **⑪ 读数是换算过的，不是原始量** ⇒ 判据改用 `img.decode()`，尺寸只作补充信息 |

> 🔴 三次的共同点：**判据看起来都在测该测的东西，而「该测的东西」的定义是我自己以为的那个。**
> 处置不是「改断言让它变绿」，而是**先把「这个量的定义是什么」查清、再重写判据**。
> 另顺手钉了两条纪律：夹具里三张图的**尺寸互不相同**（于是「加载的是哪一张」也可证）；
> 「不该有 X」的判据必须拿**部分正确**的样本当反例验一次判别力（不能拿「完全没做过的原始件」充数）。

## 十一、🔴 第二轮行为变更（2026-09-23）：静默保存 + 保存后打开文件夹

### 11.0 用户原话与三项裁决

> `改为静默保存，直接保存在原文件旁边；保存后打开文件夹；`

动手前我先做了**只读取证 + 探针实测**，确认三条能力边界，再就三个必须拍板的点提问。用户裁决：

| 待定项 | 用户裁决 | 与第一轮的差别 |
|---|---|---|
| 文件名策略 | **保留序号避让**（`_改2` / `_改3`） | 不变（第一轮同款），但**含义变了**：以前是给保存框**预填**，现在是**唯一的命名决定** |
| 「打开文件夹」怎么开 | **新标签页打开目录索引页** | 新 |
| 打开时机 | **每次保存后都打开** | 新 |

### 11.1 🔴 静默的三档 —— 「一个框都没有」是有条件的

`createWritable()` 只要句柄**有权限**就不需要用户手势：**写文件本身从来没有框**。
目录句柄已经记在库里（`dirScopeKeyOf` / `dirKeyOf`），取回来就能写 ⇒
**保存框整体退场**。连带删掉的是「一次点击只能开一个系统框 ⇒ 缺手势要退化」那一整套周旋代码 ——
**问题本身消失了，不是被优化掉了。**

但「静默」有三档，如实登记：

| # | 情形 | 用户会看到 |
|---|---|---|
| ① | **同一浏览器会话内**（权限仍有效） | **0 个框**，点一下就存好 |
| ② | **重开浏览器之后** | **1 次浏览器权限确认** —— Chrome 官方文档原话 *permissions are not always persisted between sessions*；MDN 进一步写明从 IndexedDB 取回的句柄「**很可能**」解析为 `prompt` |
| ③ | **这个目录第一次** | **目录框 + 权限确认** —— FSA 不给路径，只有用户选一次才拿得到句柄 |

> 🔴 ② 决定了 `ensureWritable` 必须排在 `saveCopy` **最前面**（在任何 picker 之前）：
> `requestPermission` **需要手势**，而它必须落在「点保存」这一次点击的手势窗口内。
> 把它排在目录框后面就晚了 —— 手势已经被那次 picker 消耗掉。

### 11.2 🔴 「打开文件夹」的能力边界（实测，不是推断）

| 问题 | 实测结论 |
|---|---|
| 能开 Windows 资源管理器吗？ | ❌ **不能**。唯一路径是 Native Messaging（另装本地宿主 + 注册表）⇒ 属**形态变更** |
| 那能开什么？ | ✅ **浏览器内的目录索引页**（`file:///C:/proj/`）：Chrome 自己渲染的名称 / 大小 / 修改日期表格，文件可点开，中文标题为 `C:\…\ 的索引` |
| 内容脚本能直接开吗？ | ❌ **不能**。实测 `typeof chrome.tabs === 'undefined'` ⇒ 必须过 background service worker ⇒ manifest 要加 `background` 字段 |
| 加 `background` 要新权限吗？ | ✅ **不要**。实测 `chrome.tabs.create` 不需要 `tabs` 权限，`permissions` 仍是 `["storage"]` |

> 🔴 **为什么不用 `window.open`**：内容脚本里 `window.open(目录URL)` 实测**也能开**，
> 但它**需要瞬态激活**，而首次保存会先弹目录框、**手势被消耗** ⇒
> 恰好在最需要它的「第一次保存」上被弹窗拦截。这类「能跑通但只在次要路径上跑通」的写法，
> 探针会给出假绿灯（主页面上测一次通过），所以**不用**。
>
> ⚠️ **标题写着「保存后打开文件夹」，但打开的不是资源管理器** —— 这是**能力边界**，不是实现取舍。
> 如实报告，不靠措辞打圆场。

### 11.3 🔴 探针挖出的真 bug：我们的工具条曾盖在刚打开的文件夹列表上

**目录索引页的 `contentType` 也是 `text/html`** ⇒ 原来的注入闸拦不住它 ⇒
刚打开文件夹，编辑器的工具条就挂在了那份列表上（探针实测 `#ep-root` = **true**）。

- **修法**：新建 `src/extension/inject-gate.ts`，判据加一条
  —— **`location.pathname` 以 `/` 结尾 ⇒ 是目录 ⇒ 不挂**。
- **为什么用这个判据**：文件 URL 不可能以斜杠结尾，这是 **URL 层面的硬事实**；
  不去认标题文案（那是**中文 locale 的产物**，换语言就失效）。
- **这个 bug 只有在「加载产品 `dist-extension/` + 走过真实保存流程」的探针里才会现形** ——
  它不在任何单测的射程内。修完实测 `#ep-root` = **false**。

> ⚠️ 探针里这条写的是「**前提 + 结论**」双断言（先确认 `contentType === 'text/html'` 且确实是目录页，
> 再断言不挂）。只断言后者的话，万一开出来的是个普通 html，**测试会「通过」而什么都没测到**。

### 11.4 构建：🔴 IIFE 不支持代码分割 ⇒ 两个入口必须分两次构建

想给 content 与 background 各出一个产物，一次构建被 Rollup **硬拒**，两条真实报错原文：

```
Invalid value for option "output.inlineDynamicImports" -
multiple inputs are not supported when "output.inlineDynamicImports" is true.
```
关掉它则换另一条：
```
UMD and IIFE output formats are not supported for code-splitting builds.
```

⇒ 拆成 `vite.extension.config.ts`（content）+ `vite.extension.bg.config.ts`（bg），
`build:extension` 顺序跑两次。🔴 **第二个 config 必须 `emptyOutDir: false`**，
否则会删掉前一次的产物 —— 症状是「扩展加载了但**完全没反应**」，很难往构建上想。

> 代价如实说：两入口**不能共享模块**，否则代码被复制成两份产物。
> 所以 `bg.ts` **刻意不 import 任何东西**（既保构建约束，也保持 background 无项目知识）。
> 于是消息名只能就地写一份字面量 —— 靠**单测读源码**（`?raw`）守两处一致，抓不到字面量即失败。

### 11.5 改了什么（模块级）

| 文件 | 改动 |
|---|---|
| `src/extension/dir-save.ts` | **整体重写**：`CopyIO` 收窄为 `{dirPicker, store}`；删 `CopySaveResult.via`；六步 → **五步**，第 ⑤ 步成为**唯一**写入路径 |
| `src/extension/bg.ts` | **新建**：background service worker，约 60 行，**零 import**，只做「收消息 → `chrome.tabs.create` → 回 `{ok}`」 |
| `src/extension/open-folder.ts` | **新建**：`requestOpenFolder(url)`，**1.5s 超时、永不抛**、读 `lastError` |

| `src/extension/ui/toast.ts` · `ui/bar.ts` | 文案：删「未弹系统框」尾巴；新增「没能自动打开那个文件夹（文件本身已存好）」；按钮名**不改**（名字描述的是**落点**，落点没变） |
| `vite.extension.config.ts` · `vite.extension.bg.config.ts` · `package.json` | 双入口构建，见 11.4 |

**两条实现纪律（写进代码注释，防复发）：**

- 🔴 **`lastError` 是「读一次」的语义**：不读会打控制台警告 `Unchecked runtime.lastError`，
  且「回调照常触发但 `lastError` 被设上」是真实世界**最常见**的失败形态 ⇒ 判据必须是「**读过且为空**」。
- 🔴 **`sendMessage` 回调可能永不触发**（扩展刚重载 / service worker 起不来）⇒ 必须自带 **1.5s 超时**，
  否则调用方 `await` 挂住，用户看到「点了保存**什么都没发生**」。
- 🔴 **`undefined`（没试）与 `false`（试了没成）绝不能混** ——
  否则「保存失败所以没开文件夹」会被报成「文件夹打不开」，归因直接反了。

### 11.8 第三轮追加（同日用户反馈）：「另存到别处」出口 + 两个「框怎么又来了」根治点

用户原话：`重新尝试、那个保存框实在是太影响效率了，权限可以提示弹窗，但是我从没见过哪个网页时先弹弹保存框再要权限的； 加一个"另存到别处"的次要按钮`。

#### 11.8.1 🔴 「先弹框、再要权限」的顺序是浏览器的，不是我们的（如实回答）

用户观察到的「目录框 → 允许修改文件」顺序**无法重排也无法去掉**，原因是结构性的：

> 授权的对象是「那个文件夹的句柄」；**句柄在你选完之前不存在** ⇒
> 浏览器只能先给你框（拿到句柄的唯一途径），再对选出来的东西问授权。
> 所有网页端「写本地文件夹」的产品（VS Code 网页版、Photopea 等）都是这个顺序。

能做的是**把它压到最少**：同一个目录只发生一次（目录级记忆）；此后是**纯权限气泡**（用户明确说可接受）；
重开浏览器后大概率也只要一次气泡（权限退化到 `prompt` 时 `ensureWritable` 先走 `requestPermission`，
**不弹框**）。框只在「库里真的没有可用句柄」时才出现。

#### 11.8.2 「另存到别处」= **一次性**出口（用户裁决的按钮）

- `saveCopy(…, { elsewhere: true })`：绕过两级记忆、**每次都弹目录框**让用户指认落点；
  写入管线（克隆清理 → 内联 → base 兜底 → `nextFreeName` → 静默写）与主路径**逐字相同**。
- 🔴 **刻意不写目录级键**：若写了，之后的静默保存会悄悄改道 —— 「存到原文件旁边」这条主承诺
  就被一次点击改掉了。只**刷「最近目录」**，供下一次目录框定位。
- 🔴 **不自动开文件夹**：自动打开的永远是「原文件旁边」（FSA 拿不到所选目录的路径），
  而这次副本偏偏不在那里 —— 打开了只会误导。提示里已报出**文件夹名**（`dir.name`）。
- 🔴 `dirMatched === false` **不构成提醒**：用户本来就指定了「不是原文件旁边」的目录，
  那里没有原文件是预期 —— 照常报警的话，这个功能每次用都会被自己吓一次。
- 提示口径换掉「已记住这个目录」那句（对它不成立），改为明确「**只这一次**」。

#### 11.8.3 🔴 两个「框怎么又来了」的根治点（都是真实缺陷，单测守住了）

1. **旧文档级键命中后不升格**：升级前的老用户命中的是 P0-9 原始的**文档级**键，而代码
   「只读不写」⇒ 同目录的**另一个**文件仍然命中不了 ⇒ 用户以为「一个目录只问一次」，
   框却再次弹出。修法：命中旧键 + 写成功 ⇒ **补写目录级键**（升格）。
2. **最近键只在首次记住时写**：注释写着「每次成功都刷最近键」，代码却只在 `!dirFromMemory`
   时调 `rememberDir` ⇒ 用户刚在 A 目录存过，下一个新目录的框却停在**更早**的位置，
   在框里多走冤枉路 —— 这正是「保存框影响效率」的一部分。修法：最近键**每次成功都刷**。

### 11.9 第四轮（同日傍晚，用户真机回报）：🔴 错落子文件夹定因 + 记忆自愈 + 「打开文件夹」整体删除

用户回报：`没存到原文件所在的文件夹，反而存到了原文件所在文件夹的一个子文件夹去了`。
三个诊断答案把因定死：子文件夹**不是** `_改`（排除旧构建残留）· 用的是**主按钮** ·
toast 里出现过「可能选错目录了」⇒ **走的是静默路径，记忆键里存的就是那个子文件夹的句柄**
——某一次在框里选岔了，之后每一次保存都被静默送进去，唯一拦截是一条转瞬即逝的 toast 附注。

#### 11.9.1 定因讨论中的一条弯路（登记防复发）

中途一度把自愈实现成「每次写入前都 `hasFile(目录, 原文件名)` 验一遍」——
**单测立刻红**：同目录的另一个文件（`b.html`）名字不同，逐次验证会把
「一个目录只问一次」这条核心承诺打碎（`记忆的粒度` 那组测试抓的）。
⇒ 修法：给目录级记忆加**信封**（`DirMemory = { h, ok }`），`ok` = 记入那一刻目录里有原文件。
只有**未核验**的记忆（裸句柄存量、`ok:false`）才逐次验证；`ok:true` 免验。

#### 11.9.2 自愈的行为（全部有单测）

1. 未核验记忆 + 目录里没有原文件 ⇒ **否决**，弹框重指认；重选成功 ⇒ 记忆重写成 `ok:true` 的信封
   （自愈闭环：此后免验直达）。结果带 `memoryRejected`，toast 解释「为什么突然有框」。
2. 重指认的框**不传 `startIn`** —— 最近键多半就是那个被否决的目录，拿它定位框会又开在错处。
3. 用户在重指认框里取消 ⇒ `cancelled`、零写盘、记忆键原值不动。
4. 否决后框弹不出来（`ensureWritable` 的权限确认吃掉手势 ⇒ picker 抛 `NotAllowedError`）⇒
   `unsupported` 如实上报、不写盘、记忆不动 —— 宁可靠一次，也不静默写进已否决的目录。
   用户再点一次保存即进重指认框。
5. 对照：`ok:true` 的信封免验（同目录另一文件 0 框 ✓）；用户**刚在框里**选的目录不匹配 ⇒
   不自愈（那一秒的决定由 `dirMatched` caveat 事后提示）。

#### 11.9.3 「保存后打开文件夹」整体删除（用户裁决）

原话：`把保存后跳转新标签页的功能删掉`。每次保存都跳一个新标签页，比「少走一步去找文件」更打断。
**整体退场，不留开关**：删 `open-folder.ts` / `bg.ts` / manifest `background` 字段 /
`vite.extension.bg.config.ts`（双构建并回单构建）/ `raw.d.ts`（只为守 bg 消息名字面量而存在）/
`folderOpened` caveat / `extension-open-folder.test.ts` / `open-folder-capability.mjs`。
构建侧回归单入口 —— §11.4 的「双 config」知识降级为历史注，**若将来再加第二个 IIFE 入口
必须重新拆 config 且后者 `emptyOutDir: false`**。目录页注入闸**保留**（手动开目录页同样不该被注入）。

### 11.11 第六轮（同日深夜，用户裁决「方案 A」）：保存永远 0 框，内联拆成独立动作

> **用户原话**：`每次保存都不得不弹那个目录选择窗吗？我从没在其他网站中见过，这是设计失误；必须解决此问题`。
> 追问「能否让弹窗自己关闭」后澄清：那是 OS 级原生框，网页无法自动关（无 close API、无编程通道）。
> ⇒ 用户拍板**方案 A**：**保存永远 0 框**，把「弹目录框」从保存动作里彻底摘出去。
> 追加 UX 要求：自包含保存（点「内联依赖」）弹原生框**之前**，先弹我们自己的面包屑 toast 说明。

#### 11.11.1 拆法（方案 A）

- **保存（下载）永远 0 框**：克隆清理 → 用**记忆里的句柄**内联（有则自包含，无则 base 兜底）→ 下载。
  保存路径**不再弹目录框**；`dirPicker` 只在「内联依赖」动作里被调。
- **内联依赖（独立动作）**：工具条新增「内联依赖」按钮（`copy` 图标）——**唯一**会弹原生目录框的入口，
  点它弹一次只读目录框拿句柄记记忆（目录级 + 最近），之后**同目录的保存自动用记忆句柄内联**（自包含，0 框）。
- **面包屑（用户要求）**：点「内联依赖」弹原生框**之前**，先用我们自己的 toast
  （`inlineDepsBreadcrumb`，90s 长时展示）说明「接下来要你选一次目录」—— 避免用户对原生框困惑。
- `saveMessage` 删 `rememberedDir`（保存不再弹框/首次记住目录），新增 `noDir`（没句柄 ⇒ 如实标不自包含并指路「内联依赖」）。
- `saveTitle` 不再预告「首次只读框」（保存本身 0 框），改为指路「内联依赖」按钮。
- 新增 `inlineDepsForSave(doc, href, io)`：弹框 → 记记忆 → 当场内联验证；返回 `{inlined, failedDeps, rememberedDir, memoryRejected, cancelled}`。
- `dirFromMemory` 自愈否决时置 `memoryRejected=true`（此前恒 false，单测抓出）。

#### 11.11.2 取舍（如实，不是缺陷）

自包含要求读到同目录依赖字节，`file://` 禁 fetch/XHR ⇒ 唯一读法是句柄（须弹框）。方案 A 把
「保存零框」与「自包含」解耦：没点过「内联依赖」的目录 ⇒ 保存不自包含（base 兜底），但**零框**；
点过一次 ⇒ 记忆里有句柄 ⇒ 之后保存自动自包含，仍**零框**。取舍由用户用按钮显式选择。
