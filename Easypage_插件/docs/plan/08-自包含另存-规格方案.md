## 2. 「自包含」只有一条路：把依赖内联进 html

已实测排除的两条路：

- ❌ **依赖留在原处 + `<base>`**（P0-8）—— 副本离开原目录，静态子资源全断。
- ❌ **把依赖复制到副本旁边** —— 只有「整个文件夹一起搬」才行；用户要的是**一份 html 能单独拉出去**。

⇒ 唯一解：把所有**渲染依赖**的内联进 html 本身。

## 4. 内联变换规格（产品实现要覆盖的）

**要内联的**（`{ 标签, 属性 }`）：

| 来源 | 目标 | 备注 |
|---|---|---|
| `<link rel=stylesheet href=X>` | `<style>` | 保留 `media`（写成 `@media` 包一层或保留属性）；`rel` 里除 `stylesheet` 外还有词则跳过 |
| `<script src=X>` | `<script>` | 🔴 **`defer` 内联后失效** ⇒ 必须挪到 `</body>` 之前；`async` 保持原位并标注语义差异 |
| `<img src=X>` | `src="data:…"` | `srcset` / `<source>` 同处理，否则窄屏取到 `srcset` 会再指向旧目录 |
| css 内 `url(…)` | `url("data:…")` | **递归**：`@import` 展开后再扫一遍；相对路径**相对引用它的那个 css 解析**（子目录依赖） |

**不动的**：`<a href>`（导航不是渲染依赖）· `data:` / `http(s):` / `//` 开头的绝对引用（本来就自包含或需联网）。

**必须处理的边界**：

1. 🔴 ~~**读不到的依赖 ⇒ 拒绝保存**，不许静默产出「看起来自包含、其实是坏的」文件。~~
   ✅ **实施后（用户裁决）**：**插 `<base>` 指向原目录绝对 URL 兜底**，并如实上报
   「这份副本不自包含，拷到别处会缺这几样」。理由——**拒绝保存等于让用户白改一场**，而兜底
   至少让副本留在原目录时一切照常。报清楚是**哪个文件**、**为什么**（不存在 / 不在所选目录内 /
   体积超限 / `<iframe>` 不支持）这一条不变。
   ⚠️ 但**绝不允许静默**：失败清单非空 ⇒ 必进 `saveCaveats`，且「不合格」这件事必须出现在提示里。
2. **页面自带 `<base href>`** ⇒ 内联时**按它**解析相对路径（P0-8 的「绝不覆盖」原则在这里变成「必须遵照」）。
   ✅ 实施后：`insertBase` 仍然检测到它就**不插**我们自己的 base，并把「没能插兜底 base」
   这件事说得更准（而不是照抄「已兜底」）。
3. **体积膨胀**：base64 使二进制膨胀 ≈ 4/3；单文件超阈值（建议 5 MB）时提示实际大小让用户决定。
   ✅ 实施后：改为**逐依赖上限** `maxBytes = 16 MB`，超限的那一个进失败清单（走 base 兜底），
   而不是整次保存失败；**没有做**「弹窗让用户决定」——那会多开一个系统框，而一次点击只能开一个。
4. **`<script>` 内联的时机**：内联脚本在解析到它的位置**立即执行**，与原 `<script src>` 同步加载的时机**基本一致**，唯一差别是 `defer`（见上）。
   ✅ 实施后：`defer` 的脚本**整段挪到 `</body>` 之前**（`copy.body.appendChild`），保住「解析完 DOM 再执行」。
   ⚠️ 另外补了一条规格里没写的：**`<script>` / `<style>` 是原始文本元素**，
   内容里出现 `</script` 会把标签提前截断 ⇒ 必须转义成 `<\/script`。

## 6. 读取依赖内容的通道

内联需要**读到依赖的字节**，而内容脚本读不到本地文件（P0-8 §2.1 已实测：页面/content script 的
`fetch` / `XHR` / `cssRules` 全被拦，加不加 file host_permissions 一样）。

| 通道 | 状态 |
|---|---|
| **目录句柄** `dir.getFileHandle(rel).getFile()` → `.arrayBuffer()` | ✅ **已实现（`dirReader`）**。⚠️ 真实目录句柄下的读写仍是**人手门禁 G1**（要真人点目录框才拿得到句柄）。优势：权限面与现在**完全相同**（用户已经选过那个目录）、无需 SW 通信、支持子目录与二进制。**只读该目录的下层**（`..` 一律拒） |
| 扩展 Service Worker `fetch(绝对 file:// URL)` | ✅ 已实测通（P0-7 探针，甚至不需要 file host_permissions）；代价是要加一层 content script ↔ SW 消息 |
| ⚠️ 跨目录依赖（`../shared/x.css`） | 目录句柄**读不到上层** ⇒ 报「不在所选目录内」，由调用方插 base 兜底。SW 通道留作后续扩展，本期不做 |

⇒ ✅ 实施后：**主用目录句柄**（`dirReader`）。它有一条**曾违反自己文件头契约**的真 bug，单测抓到了：
契约写着「**读不到一律返回 null，永不抛**」，而实现只把「路径解析」包住了 —— `getFileHandle` /
`getFile` 抛的 `NotFoundError` / `NotAllowedError` 直接漏出去 ⇒ 调用方拿到的是「**内联流程崩了**」
而不是「读不到」。这两件事的**处置完全不同**：前者进失败清单走 base 兜底，后者让整次保存失败。
⇒ 修法：整段 `try/catch` 兜住。**「实现必须对得上自己写下的契约」—— 这是又一个具体案例。**

> 🔴 **G1 的判据为什么要先自测**：那 11 条正则在真人跑这一轮之前**一次都没被执行过**。
> 万一某条写错（比如 `url("data:` 那里的引号），用户会白跑一趟人工流程，
> 且会把 FAIL 读成「产品坏了」—— 那正是本项目最怕的那类假证据。
> 第一次设计的自测**还有个洞**：反例拿的是「未内联的原文件」，而它既没有 `<base>` 也没有残留，
> 于是「不该有 X」那一类判据对它**一律为绿**，自测会把这种绿报成通过 —— 什么都没证明。
> 换成「**部分内联**」当反例（带 base + 外链 + 编辑器残留）之后，11 条才条条有判别力。

## 8. 明确不做

- ❌ 内联 `<a href>` 指向的其它页面（那是导航，不是渲染依赖）。
- ❌ 把 `fetch`/XHR 的运行时请求也「内联」（客户端转换做不到，且 `file://` 上本来就通不过）。
- ❌ 修改 `<script>` 的**逻辑**（只搬位置，不改内容）。
- ❌ 沿用 `_改/` 子文件夹（本方案取代它）。
- ⚠️ `<base>` 注入**没有整个删掉**：它从「主路径」降级为「有依赖没内联进来时的**兜底**」。
  这是用户裁决 ③ 的直接结果 —— 与上面 §4-1 一致。
