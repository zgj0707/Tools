## 1. 实测基础（本方案的事实依据）

新增探针 `qa/probes/file-protocol-capability.mjs`，真实 Chromium 实测：

```bash
node qa/probes/file-protocol-capability.mjs
# JSON → test-results/capability/file-protocol-capability.json
```

| 能力 | `file://` 实测 | `http://127.0.0.1` 对照 |
|---|---|---|
| `isSecureContext` | **true** | true |
| `showSaveFilePicker` / `showOpenFilePicker` / `showDirectoryPicker` | **全部存在** | 全部存在 |
| 真实调用 `showSaveFilePicker` | **`AbortError`** | — |
| `input[type=file]`+`FileReader`、`URL.createObjectURL`、`a[download]`、`clipboard.writeText` | 全部可用 | 全部可用 |
| `document.cookie` 可写 | **false** | true |
| 跨本地文件 `localStorage` | 🔴 **共享同一个 `file://` origin** | — |

> **`AbortError` 是决定性读数。** 它说明调用**已通过安全检查、走到"弹出原生选择框"那一步**，仅因无头浏览器没有对话框而中止。
> 若被协议策略拦截，错误名会是 `SecurityError`；若缺用户手势，会是 `NotAllowedError`。两者都不是。
>
> 网上多方称"`file://` 不是安全上下文、FSA 不可用、需 `--unsafely-treat-insecure-origin-as-secure`（该参数 Chrome 94+ 已弃用）"——
> **实测全部不成立**。这类说法混淆了「页面脚本调 FSA」与「扩展沙箱进程读 `file://`」，两者是不同的限制。

**唯一未验完的一环**：原生对话框真的弹出并返回文件句柄（无头环境无法弹原生框）。验收方式见 §8 门禁 G1。

**已知但仍成立的边界**（来源：StackOverflow，未本机复验）：
- content script 里 XHR `file://` 会被 `origin 'null'` + CORS 拒绝
- MV3 service worker 的 `fetch` 只支持 `http` / `https`
- MV2 的 `chrome.fileSystem` 在 MV3 已移除

⇒ 写回的正解 = **在页面上下文直接调 FSA**；兜底 = `chrome.downloads` API 与 `a[download]` blob。

### 1.1 扩展加载能力实测（门禁 G2，已完成）

新增探针 `qa/probes/extension-load-capability.mjs`：构建一个最小 MV3 扩展（`content_scripts.matches` = `file:///*` + `http://127.0.0.1/*`），用 `launchPersistentContext` + `--load-extension` 加载。

| 模式 | 扩展加载 | `http://127.0.0.1` 注入 | `file://` 注入 |
|---|---|---|---|
| `headless: true` | ❌ 失败 | NOT-INJECTED | NOT-INJECTED |
| `headless: false`（有头） | ✅ 成功 | ✅ `injected` | ✅ **`injected`** |

**两条定论**：

1. 🔴 **e2e 必须改为有头串行**（`headless: false` + `--workers=1`）。Playwright 的默认无头模式**加载不了 unpacked 扩展**，
   因此 §7「headless 下加载扩展」的风险项关闭，改为一条既定的工程约束。
2. ✅ **开发期无需手动勾「可访问文件网址」**：有头模式下 unpacked 扩展**直接注入 `file://` 成功**。
   且在该 file:// 页面内 `isSecureContext = true`、`showSaveFilePicker` 存在——在 content script 注入后的**真实页面上下文**里
   第二次独立确认了 §1 的结论。
   > ⚠️ 边界：此结论适用于 `--load-extension` 的开发/自用场景。**发布给他人安装时仍应在引导中说明该开关**，
   > 不要假设所有用户环境默认开启。

### 1.2 Shadow DOM 对 Playwright 选择器的影响实测（更正 §4.2 的早期判断）

本方案早期草案断言「覆盖层进 Shadow DOM ⇒ Playwright 的选择器不穿透 ⇒ e2e 锚点体系需要改造」。该判断**未经实测**，
而它直接决定 P0 的成本量级，故新增探针 `qa/probes/shadow-dom-locators.mjs` 实测：构造与 `host.ts` 计划同构的页面
（宿主 `div#ep-root` + `attachShadow({mode:'open'})`，覆盖层与工具条都在 shadow 内部），逐种定位方式验证。

| 定位方式 | 结果 |
|---|---|
| `css=#id` / `css=.class` / 属性选择器 `[data-dir="se"]` / 后代组合 `.ep-toolstrip button` | ✅ 穿透 |
| `getByRole(button, {name})` 及其 `{exact:true}` 变体 | ✅ 穿透 |
| `getByText` / `getByTitle` | ✅ 穿透 |
| `click()` 可交互 · `boundingBox()` 可量测 · `page.evaluate` 可访问 `shadowRoot` | ✅ 通过 |
| **【反例】** `xpath=//*[@id=...]` | ❌ `count=0`，**确认不穿透** |
| **【反例】** 「light DOM 限定后代」如 `body > #ep-btn-bold` | ❌ `count=0`，**确认不穿透** |

**定论：锚点体系可原样复用，改动量为 0。** 现有 23 个 spec 中只有 `list.spec.ts` 用了 2 处 xpath，
且其目标是被编辑页面里的 `#a` / `#u`（用户内容）—— 插件形态下那部分位于顶层 `document`、**根本不进 shadow root**。
约束只有一条，写进纪律即可：**编辑器 UI 的断言只用 CSS / `getBy*`，不得用 XPath 或 light-DOM 限定后代选择器。**

### 1.3 浏览器渠道对 unpacked 扩展的加载能力实测（决定「用户怎么装」）

§1.1 证明了「有头 + `--load-extension` 可以注入 `file://`」，但它没回答一个更前置的问题：**哪些浏览器认这个参数。**
本机实测出现反直觉结果，故补 A/B 探针 `qa/probes/browser-channel-extension-capability.mjs`：
同一 harness（`launchPersistentContext` + `--load-extension=<dir>` + 同一 `file://` fixture + 同一判定脚本），
**唯一变量是 `executablePath`**。

| 渠道 | 版本 | 扩展注入 | 判定依据 |
|---|---|---|---|
| Playwright 自带 Chromium | 1243 | ✅ 可注入 | 宿主 `#ep-root` + shadow 内工具条均就位 |
| 系统 Google Chrome | 153.0.8010.48 | ❌ **不注入** | 该渠道忽略了 `--load-extension` |
| 系统 Microsoft Edge | 当前稳定版 | ✅ 可注入 | 宿主 + shadow 内工具条均就位 |

**三条定论**：

1. 🔴 **Chrome 137 起，品牌版 Google Chrome 不再接受 `--load-extension`**（该能力只保留在 Chromium / Chrome for Testing /
   Edge 这类渠道）。这直接否掉了「给用户的 Chrome 发一个双击启动器」这条最省事的分发路径。
2. 🔴 **失败是静默的**：浏览器正常打开、页面正常显示、**无任何报错**，只是插件不在。
   ⇒ 新增纪律：**「扩展装没装上」不能靠「浏览器起来了」推断，必须去页面里找 `#ep-root`。**
   `scripts/open-with-easypage.mjs --verify` 就是为此而生（CDP 连上后轮询 `#ep-root` 与工具条尺寸）。
3. ⚠️ **对真实用户的分发路径仍未解决**：Chrome 137+ 用户只能走 `chrome://extensions` 手动「加载已解压的扩展程序」，
   并手动打开该扩展的「允许访问文件网址」；该步骤是**原生目录选择框，无法自动化**。
   发布前必须给出「人话引导」（截图 + 分步），不能指望一句「加载一下」。
   > 注：`--load-extension` 路径下**不需要**开这个开关（§1.1 已实测）；只有手动加载路径才需要。

**落地**：`scripts/open-with-easypage.mjs`（薄包装 `open-with-easypage.cmd`）按上述矩阵自动选载体 ——
优先级 `--browser / EASYPAGE_BROWSER` > 可用 Chrome（**仅当主版本 ≤ 136**） > Edge > Playwright Chromium；
`--dry-run` 逐条打印「为什么跳过某渠道」，`--verify` 把「静默不加载」变成明确结论。
实测输出：`[✓] 已验证：扩展注入成功，工具条在页面上 / 工具条 223×34`。

## 2. 产品定位（本次转向后的唯一定义）

> **一份已经存在的本地 HTML 文件，在浏览器里打开它，挂上工具栏就地改内容与样式，改完存回同一份文件。**

三条不可放弃的性质，任何一条被放弃，产品就失去存在理由：

1. **进出都是同一份 HTML 文件** —— Figma 不吃 HTML、Canva 的产物是托管链接（证据链见 `2026-09-22.md`）
2. **不动文档流结构** —— 改完结构关系不变，所以**改不坏**
3. **不离开本机** —— 零登录、零上传、`file://` 直接打开

**判据（用于裁决任何新功能提案）**：

> 这条改造，服务的是「**改**」还是「**设计**」？服务「设计」的一律不做。
> 「对标」不是一个合法理由——它没有停止条件。

## 3. 为什么是 MV3 扩展，不是 bookmarklet

| 判据 | MV3 扩展 | bookmarklet |
|---|---|---|
| 写回原文件 | 页面内直调 FSA；另有 `chrome.downloads` 兜底 | ❌ 只能触发下载 |
| 偏好持久化 | `chrome.storage`，干净 | ❌ 只能用页面 `localStorage`，**被 §1 第 6 行实测证实会跨文件污染** |
| 注入 `file://` | ✅ 需用户**一次性**开「可访问文件网址」 | ⚠️ 对本地文件 CSP 更脆弱 |
| 内核体积 | ✅ 打包无限制 | ❌ 整包 4,500 行 TS 要塞进书签 URL |
| 每次使用 | ✅ 打开本地 html **自动挂载** | ❌ 每次手动点一次书签 |

**一次性成本**：装扩展 + 在 `chrome://extensions` → 详细信息 → 站点权限 勾「可访问文件网址」。
范围既已限定「仅本地 html」，这个成本换来的能力差距是压倒性的。**不支持 Firefox**（需另一套 manifest 与垫片，本期不做）。

## 4. 架构

### 4.1 目录与产物

```
src/
├── core/          ← 原样保留（1,775 行，零第三方依赖，与宿主无关）
├── app/           ← 保留编辑器 UI（panels / canvas / menus / i18n / icons）
├── adapters/      ← interaction 保留；preview、dom 废弃
└── extension/     ← 新增
    ├── manifest.json
    ├── content.ts        注入入口：装配内核、挂 Shadow 宿主、注册变化监听
    ├── host.ts           取代 CanvasHost：宿主 = 目标 document
    ├── watch.ts          DOM 变化监听 + 覆盖层重定位 + 事件仲裁（🔴 全新）
    ├── save.ts           写回原文件（FSA）+ chrome.downloads 兜底
    └── popup/            开关、保存、设置
```

构建：`vite build` 增加一个 IIFE 目标产出 `dist-extension/`，content script 不含 ESM（MV3 content script 不支持 ES module），内核以单文件 bundle 注入。

### 4.2 注入与隔离

- 宿主容器：`<div id="ep-root">` + `attachShadow({ mode: 'open' })`
- `app.css`（806 行）与 `tokens.css`（84 行）**全部进 Shadow DOM**，不注入 light DOM
  - 理由：目标页面的 CSS 会打乱注入 UI（`.ep-*` 类名没有优先级保障）
- 覆盖层（选中框/手柄/参考线）也进 Shadow DOM
  - ✅ **代价几乎为零（2026-09-22 实测，见 §1.2）**：Playwright 的 CSS / `getByRole` / `getByText` /
    `getByTitle` / `click` / `boundingBox` / `page.evaluate` **全部穿透 open shadow root**。
    不穿透的只有 XPath 与「light DOM 限定后代」两类 —— 而现有 23 个 spec 里只有 `list.spec.ts`
    用了 2 处 xpath，且指向**被编辑内容**（插件形态下那部分在顶层 document、根本不进 shadow root）。
    ⇒ **锚点体系可原样复用，改动量为 0。** 这条代价在本方案的早期草案里被高估了。

### 4.3 宿主替换（`CanvasHost` 189 行 → 重写）

| 现实现 | 新实现 |
|---|---|
| 建两个 iframe，编辑帧 / 预览帧 | 无 iframe，直接在目标 `document` 上操作 |
| `frameRect = iframe.getBoundingClientRect()` | 坐标基准 = 文档坐标；视口变化靠 scroll/resize 重算 |
| iframe 内坐标稳定，不需要跟随滚动 | 🔴 **页面会滚动、会变长** ⇒ 覆盖层必须跟随重算 |
| 预览帧（`allow-scripts`）承担"看效果" | ❌ 废弃：插件形态下**所见即所得**，没有预览这一步 |
| `zoom.ts` / `ZoomController` | ❌ 废弃：缩放交给浏览器 `Ctrl+±` |

### 4.4 保存策略（🔴 已定案；2026-09-23 同日**第二次**转向，以 P0-9 版为准）

**第一次（P0-8）**：用户裁决「不覆写原文件；复制 css/js 并新建文件夹 `_改` 存放」⇒ 原三选一作废，
改为**旁路另存到 `<原目录>/_改/`**，依赖不复制、靠 `<base href="../">` 指回原目录。

**第二次（P0-9，当前）**：用户重新梳理，原话 ——

> `保存应该是 点击保存键-自动定位到原文件所在处-点击保存-自动将文件改名为 *原文件名*_改 ；
> 新文件应该是自包含的，可以直接拉出去被分享`

这**推翻了 P0-8 的两条核心决定**：落点从 `_改/` 子文件夹改为**同目录 `原名_改.html`**；
完备性从「依赖留原处 + base」改为**内联自包含**。P0-8 的定案表整体作废，现行口径：

| 落点 | **原文件旁边**，名字 `原名_改.html`；重名则追加序号（`原名_改2.html`）⇒ **原文件逐字节不变** |
| 目录怎么来 | 让用户用 `showDirectoryPicker` **选一次**，句柄按**目录**记忆（`dirScopeKeyOf`），同目录之后**不再问** |

## 6. 内联 SVG 编辑设计（用户选定优先做）

页面上的图形态决定可行边界（如实标注）：

| 页面上的图是什么 | 能否真改结构 | 原因 |
|---|---|---|
| **内联 `<svg>`** | ✅ **可以**（本期做） | 节点 `rect`/`circle`/`path` 与连线 `line`/`path` 都是 DOM 元素 |
| `<div>` + 定位 | ✅ 可以 | 就是改 `style` |
| mermaid 渲染出的 SVG | ⚠️ 有条件 | 页面保留源码时**下次重渲染会还原**；且 mermaid 自算定位，拖动后连线不跟随 |
| `<canvas>` | ❌ 不行 | DOM 里只有一个 `<canvas>`，节点连线是像素 |
| `<img>` 截图 | ❌ 不行 | 本质是图片，除非 OCR / 矢量化 |

> 🔴 **必须提前决定的取舍**：改的是「渲染结果」还是「源数据」？
> 若页面含渲染脚本（mermaid 等），改渲染结果 = **每次打开都白改**。这种情况下正确做法是先把图**固化**成内联 SVG，或去改源码文本。

### 复用与新增

| 能力 | 复用 | 说明 |
|---|---|---|
| 图形悬停 / 选中 | ✅ `OverlayLayer` + `geom` | SVG 元素同样有 `getBoundingClientRect()`，选中框逻辑可复用 |
| 拖动节点 | ✅ `SelfInteractionAdapter` + `transform` | SVG 元素支持 `transform` 属性，与 README §9 的路线一致 |
| 改标签文字 | ⚠️ `InlineTextEditor` 需改造 | SVG `<text>` 的 `contentEditable` 支持不一致，改用 overlay input 层 |
| **改连线端点** | 🔴 新增 | 需解析 `<line>` 的 `x1/y1/x2/y2` 与 `<path>` 的 `d` 属性 |
| **新增箭头 / 节点** | 🔴 新增 | 需定位目标 `<svg>` 并 append，且插入物必须可完全清除 |
| **SVG 坐标系换算** | 🔴 新增 | `viewBox` + `preserveAspectRatio` 下，屏幕像素 ↔ SVG user units 需换算 |

**新增物一律遵守铁律 8**：`data-ep-*` / `.ep__` 前缀、进 `#ep-overlay-root`，导出时 `stripArtifacts` 必须能全部清除。

## 8. 分期与门禁

### 迁移策略：增量并存，不做一次性替换（2026-09-22 定案）

P0 影响面已量化：23 个 spec 里 **22 个依赖 iframe 宿主**（`frameLocator` 最高 `shortcuts` 9 次），
只有 `smoke.spec.ts` 完全不碰。若走「一次性把宿主换掉」的路线，这 22 个 spec 会在移植期间全部失效
—— 等于**在最需要回归网的时候先把回归网拆了**。故本方案采取增量路线：

1. `src/extension/**` 与旧入口**并存**：扩展是新增入口，不动旧入口；
2. 旧 `index.html` 应用与其 **84 个 e2e 用例继续作为回归网**，必须保持全绿；
   任一批提交让它们变红，即视为回归（而不是「预期内的迁移代价」）；
3. 扩展侧按 P0 / P1 分期长出新基座（`file://` fixture + 有头加载扩展）；
4. 某一能力在扩展侧达到**可验证的等价**之后，才把对应 spec 迁过去；**不做预迁移**；
5. 旧外壳（`App.ts` 1280 行 + 预览覆盖层 + 缩放控制器）在扩展侧不再依赖它之后才删除。

**每批提交的判据**：`npm run check` 通过 + 旧 e2e 全绿 + 扩展侧探针全绿，三条同时成立。

- ❌ 任意线上页面（含他人网站）——拿不到源码、运行时 DOM 与源 HTML 不一致
- ❌ 预览覆盖层、缩放控制器（插件形态下无意义）
- ❌ 云同步、账号、协作、上传
- ❌ `<canvas>` / `<img>` 形态的图形编辑
- ❌ 从零建站、Flex/Grid 结构可视化重构、组件市场
- ❌ 「对标 Figma」类功能：间距标注、尺寸徽标、上下文浮条、全站图标化（判据见 §2）
